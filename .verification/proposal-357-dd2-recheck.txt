## What to build

Establish the shared append-only Evidence correction foundation and deliver the observation-correction tracer bullet end to end. ## Acceptance criteria

* [ ] Every observation correction is an immutable `EvidenceCorrectionId` act targeting exactly one `EvidenceObservationId` root or earlier observation correction from that same root; ancestry is acyclic and uses the shared closed `EvidenceFactRef` identity contract.

* [ ] `REVISE` carries the complete observation replacement assertion; `RETRACT` withdraws its target without inventing `RESTORE`, `CONTEST`, `SUPERSEDE`, `QUALIFY`, or `DISCONFIRM` Evidence correction effects.
* [ ] Retraction recursively restores the immediately preceding branch interpretation; siblings remain independent; materially equivalent surviving assertions coalesce with complete support; incompatible positive branches or positive-versus-withdrawal support yield `CONTESTED`.
* [ ] Recency, UUID ordering, database ordering, and latest-write-wins never choose truth; missing or unknown ancestry is invalid or incomplete history rather than contestation.
* [ ] Exact replay remains idempotent and changed semantic `OperationId` reuse is rejected.
* [ ] Domain/application and PostgreSQL integration tests prove observation revision, retraction, restoration, sibling/coalesced support, contestation, invalid ancestry/cycles, append-only history, rollback, restart reconstruction, and the inward-owned greenfield persistence boundary.

ACTION 3 — CREATE NEW-ASSESSMENT-CORRECTION
Title: Correct sufficiency assessments with derived proof and trusted revalidation
Complete proposed body:

## Parent

Parent Spec: #357

## Spec obligations

US-3, US-12, ID-2, ID-12, ID-20, TD-2, TD-5, TD-9

## Architecture obligations

ARCHSRC-2, ARCHSRC-4, ARCHSRC-7

## Architecture context

Evidence; Configuration; Application Use Cases; Durable Persistence; ADRs 0011, 0012, 0013, and 0014. All architecture and material design decisions currently required by this ticket are accepted; no known implementation-readiness blocker remains unresolved.

## Context fit

indivisible-two-window-exception — ADR 0014 requires an assessment-correction replacement to be Evidence-derived from the complete authoritative universe and freshly re-evaluated/revalidated at the trusted commit instant before the same append becomes authoritative. Separating those two halves would leave an intermediate append path capable of persisting caller-authored or stale sufficiency proof, so this semantic cutover cannot be made green as two independent tickets.

## What to build

Add sufficiency-assessment `REVISE | RETRACT` as the assessment-specific extension of the shared Evidence correction algebra. A `REVISE` of a misrecorded assessment must derive its complete replacement disposition/proof through the Evidence-owned deterministic evaluator over the authoritative requirement set/version and complete interpreted binding/correction universe; callers cannot author the authoritative disposition or select the authoritative support subset. Preserve same-root correction only for the same attributable assessment boundary and requirement-set/version contract. Reassessment caused by time, new Evidence, or changed requirements creates a new `EvidenceSufficiencyAssessmentId` root, with changed requirement version always creating a new reassessment root. At the trusted commit instant, freshly re-evaluate the replacement assessment and atomically revalidate the exact requirement assignment/version, complete binding and correction universe, support version, temporal freshness, and relied-upon negative predicates before append.

## Acceptance criteria

* [ ] Each assessment correction is an immutable `EvidenceCorrectionId` targeting exactly one `EvidenceSufficiencyAssessmentId` root or earlier assessment correction from that same root; ancestry is acyclic and uses the shared `REVISE | RETRACT` algebra.
* [ ] Assessment `REVISE` carries a complete replacement assertion whose disposition, contributors, deficiency witnesses, counted observations, freshness/no-freshness basis, negative witnesses, `EvidenceSupportVersion`, and absence guards are derived by Evidence from the complete exact-key interpreted binding/correction universe; caller-authored authoritative results or caller-selected authoritative support subsets are rejected.
* [ ] A correction may retain the assessment root only for a misrecorded assertion at the same attributable assessment boundary and authoritative requirement set/version. Reassessment caused by time, new Evidence, or changed requirements creates a new assessment root; a changed requirement-set version may never be represented as correction of the existing assessment root.
* [ ] `RETRACT` withdraws its target and recursive interpretation restores the immediately preceding branch state; sibling branches remain independent, materially equivalent surviving assertions coalesce with complete support, and incompatible surviving support yields `CONTESTED` without recency/UUID/database ordering.
* [ ] At a fresh trusted commit instant, Evidence re-runs deterministic assessment derivation at commit `T=K` and atomically revalidates the exact requirement version/assignment, complete binding and correction universe, support version, temporal freshness, and typed negative predicates before appending the correction. Matching stored versions alone are insufficient.
* [ ] Missing, unavailable, contested, incomplete, or invalid requirement authority; unavailable cross-owner revalidation; stale basis including time-only freshness change; invalid history; or persistence failure appends no assessment correction and remains typed/fail-closed.
* [ ] Historical assessment proof and prior corrections remain immutable and inspectable; exact replay is idempotent and changed semantic `OperationId` reuse is rejected.
* [ ] Domain/application tests and real PostgreSQL migration, round-trip, rollback, restart, and concurrency tests cover assessment revision/retraction/restoration/contestation, derived replacement proof, changed-requirement/new-root behavior, caller-authored proof rejection, commit-time re-evaluation, time-only invalidation, corrected-binding-universe changes, and greenfield inward-owned persistence constraints.
