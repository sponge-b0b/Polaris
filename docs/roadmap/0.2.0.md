# Polaris 0.2.0 Greenfield Roadmap

**Status:** Approved  
**Release:** 0.2.0  
**Approved:** 2026-09-04  
**Purpose:** Sequence delivery of the approved 0.2.0 requirements without allowing legacy implementation topology to define the plan.

## Roadmap authority

This roadmap is derived from the approved [`../product/requirements-0.2.0.md`](../product/requirements-0.2.0.md), the frozen product/domain doctrine under `docs/product/`, and the canonical vocabulary in [`../../CONTEXT.md`](../../CONTEXT.md).

It is a **product-delivery roadmap**, not an architecture or implementation plan.

The pre-greenfield roadmap under `legacy/v0_1/docs/roadmap/` is historical donor/reference material only. It does not define milestone order, architecture, component ownership, dependencies, or release acceptance for the greenfield system.

## Release objective

Polaris 0.2.0 must establish one coherent greenfield portfolio-decision system that is narrow in supported breadth but complete in its load-bearing semantics.

The roadmap therefore optimizes for:

```text
first-class Investment Decision semantics
        +
end-to-end decision continuity
        +
trustworthy historical reconstruction
        +
explicit authority boundaries
        +
small, useful supported breadth
```

It does not optimize for preserving legacy components, maximizing feature count, reproducing every former integration, or rebuilding horizontal platform machinery before the decision product needs it.

## Delivery rules

1. **Product semantics before implementation topology.** Milestones are expressed in decision-system outcomes and acceptance scenarios, not legacy packages or workflows.
2. **Architecture before implementation.** Greenfield architecture and required component boundaries must be approved before production implementation begins.
3. **Vertical usefulness before platform breadth.** Prefer the smallest coherent end-to-end decision path over broad collections of disconnected capabilities.
4. **Just-in-time supporting infrastructure.** Reliability, observability, integrations, configuration, security, persistence, AI infrastructure, and similar platform work should be introduced when required by an owned product responsibility, not as speculative framework construction.
5. **Donor inspection follows ownership.** A legacy component may be inspected for salvage only after the relevant requirement and current architectural owner exist.
6. **Reuse means transplantation.** No milestone may satisfy a requirement through runtime dependency on `legacy/`.
7. **History must stay honest during development.** Temporary implementation shortcuts may not collapse canonical domain distinctions merely because a later milestone intends to restore them.
8. **Milestone completion is evidence-based.** A milestone is complete only when its exit criteria are demonstrated through durable documentation, executable verification, product-level acceptance evidence, or an equivalent objective check.

## Sequence

```text
R0  Product/domain reset + greenfield cutover + requirements     COMPLETE
        ↓
R1  Greenfield architecture and component ownership             NEXT
        ↓
R2  Durable decision kernel and historical truth
        ↓
R3  First coherent human decision slice
        ↓
R4  Governed consequential decision path
        ↓
R5  External action continuity and reconciliation
        ↓
R6  Attentive closed-loop learning
        ↓
R7  Release hardening and 0.2.0 acceptance
```

The milestones are deliberately cumulative. Later milestones deepen the same decision system rather than establishing unrelated product tracks.

# R0 — Product/domain reset, cutover, and requirements

**Status:** Complete

## Objective

Establish the greenfield authority chain before architecture or implementation can inherit old assumptions.

## Completed outcomes

- product and domain doctrine frozen sufficiently for 0.2.0 work;
- domain-discovery Definition-of-Done audit GREEN;
- pre-greenfield delivery frontier retired;
- pristine v0.1 implementation tagged `legacy-v0.1-baseline`;
- pre-greenfield platform quarantined under `legacy/v0_1/`;
- fresh `src/polaris/` package boundary established;
- runtime/import dependency on `legacy/` prohibited;
- 0.2.0 requirements reconstructed from current product/domain authority rather than legacy implementation;
- 0.2.0 requirements approved.

## Exit condition

R0 is complete when requirements are approved and architecture is authorized without any legacy architecture becoming the default baseline.

# R1 — Greenfield architecture and component ownership

**Status:** Next

## Objective

Define the smallest architecture capable of satisfying the approved requirements while keeping Investment Decision semantics, Durable Decision Memory, authority, external factual authority, and supporting platform concerns on the correct side of their boundaries.

## Required outcomes

Architecture must establish, at minimum:

- the system boundary and major responsibility owners;
- dependency direction;
- how business truth is established and persisted independently of runtime execution artifacts;
- how first-class Investment Decision identity and lifecycle are owned;
- how Durable Decision Memory spans the lifecycle without becoming a generic workflow archive;
- how Decision Context, Evidence provenance, Judgment-Time Availability, and freshness are represented across boundaries;
- how Polaris investment judgment, deterministic rules, human power-specific authority, and external execution authority remain separate;
- how authoritative external Portfolio State and external activity enter the system;
- how one human-usable decision surface reaches the same shared decision semantics;
- where supporting responsibilities such as integrations, AI/model access, configuration, reliability, observability, and security belong;
- measurable initial operational targets appropriate to decision-time use;
- an enforceable dependency rule preventing current code from importing or executing through `legacy/`.

## Constraints

R1 must not:

- select architecture because it resembles v0.1;
- require a workflow engine, agent topology, event bus, RAG system, plugin framework, generic runtime, or database design unless the approved requirements justify it;
- inspect legacy components for reuse before their current architectural owner and need are established;
- decompose the system into services or packages merely because a capability name exists in the product model.

## Exit criteria

R1 is complete when:

1. the greenfield architecture is durably documented and approved;
2. every approved requirement family has a clear architectural owner or cross-cutting enforcement boundary;
3. dependency direction and business-truth ownership are explicit;
4. no architectural answer depends on `legacy/` as current authority;
5. the required component boundaries are clear enough to begin selective donor inspection and implementation planning.

## Requirement coverage emphasis

Primary requirements: `GF-*`, `DEC-*`, `MEM-*`, `AUT-*`, `INT-*`, `REL-*`, `SEC-*`, `TMP-*`.

# R2 — Durable decision kernel and historical truth

**Status:** Planned

## Objective

Establish the smallest durable business core that can represent an Investment Decision faithfully through time before sophisticated reasoning or broad integrations are added.

## Product outcomes

The supported path must be able to:

- establish a Decision Need and first-class Investment Decision identity;
- preserve Subject, Decision Scope, Decision Context, and identity as distinct concepts;
- distinguish unresolved, deferred, substantively resolved, externally resolved, superseded, and renewed-decision relationships according to the frozen domain semantics;
- persist material decision-domain state across process boundaries;
- preserve non-destructive historical state and temporal relationships;
- reconstruct what decision state existed at relevant historical times;
- preserve actor attribution separately from technical provenance;
- keep Durable Decision Memory independent of workflow/job/report/model identity;
- query durable decision history without replaying legacy runtime artifacts.

## Acceptance emphasis

This milestone should establish the semantic foundation for:

- `AS-001` New material Decision Need;
- `AS-002` Same unresolved decision resumes;
- `AS-003` Deferral and later resumption;
- `AS-004` Resolved decision followed by renewed judgment;
- `AS-005` External Resolution;
- `AS-022` Legacy isolation.

The milestone does not need to complete every analytical capability. It must make later capabilities unable to redefine Investment Decision identity for their own convenience.

## Exit criteria

- decision identity and lifecycle invariants are executable and durable;
- retry/recovery cannot duplicate or rewrite already committed business truth;
- historical reconstruction can distinguish current state from prior attributable state;
- current production/test paths remain independent of `legacy/`.

# R3 — First coherent human decision slice

**Status:** Planned

## Objective

Deliver the first genuinely useful end-to-end Polaris decision path using intentionally narrow breadth.

The preferred slice should use one small supported Portfolio/instrument universe, the minimum trustworthy Evidence sources needed for the scenario, and one human-usable decision surface. Breadth is not the goal; semantic coherence is.

## Product outcomes

The slice must support:

```text
user-initiated or otherwise attributable Decision Need
        ↓
Decision Context + attributable Evidence
        ↓
Investment reasoning + meaningful challenge
        ↓
Projected Portfolio Consequences + Portfolio Risk
        ↓
Investment Recommendation or justified withholding
        ↓
Human Investment Decision
        ↓
Outcome
        ↓
Decision Evaluation
        ↓
Lesson
```

A deliberate hold/no-action path is sufficient for the first closed slice and correctly requires zero synthetic Action Intents.

## Required semantics

- Evidence provenance and Judgment-Time Availability;
- material Conflicting Evidence and Investment Uncertainty remain inspectable;
- Portfolio Risk participates in Recommendation formation;
- Recommendation and Human Investment Decision remain separate;
- human modification/rejection is preserved without rewriting Polaris judgment;
- human decision without a Recommendation remains possible;
- Outcome, Decision Evaluation, and Lesson remain distinct;
- the human surface exposes shared decision semantics rather than a report-specific reconstruction.

## Acceptance emphasis

- `AS-006` Stale Evidence blocks current support;
- `AS-007` Conflicting Evidence and meaningful challenge;
- `AS-008` Portfolio Risk changes the recommendation;
- `AS-011` Human modifies or rejects Recommendation;
- `AS-012` Human decision without Recommendation;
- `AS-013` Hold/no-action with zero Action Intents;
- `AS-017` Historical reconstruction without hindsight;
- `AS-018` Favorable Outcome from weak process;
- `AS-019` Unfavorable Outcome from sound process.

## Exit criteria

A human can use one supported path to make and later inspect a real Polaris Investment Decision without depending on legacy runtime semantics, and the resulting history is sufficient for a meaningful hindsight-safe Decision Evaluation.

# R4 — Governed consequential decision path

**Status:** Planned

## Objective

Extend the coherent decision slice so a capital-relevant Recommendation and Human Investment Decision can cross governed boundaries without collapsing deterministic rules, Polaris judgment, or power-specific human authority.

## Product outcomes

The supported path must demonstrate:

- Evidence sufficiency and freshness as real boundary conditions;
- explicit Policy results where applicable;
- explicit Formal Constraint results where applicable;
- Admissibility as distinct from Approval and Recommendation quality;
- attributable Approval or Authority Denial when required;
- Mandate Exception and Residual-Risk Acceptance as separate powers when applicable;
- attributable Human Investment Decision;
- positive authority provenance rather than inference from absence of failure;
- fail-closed behavior when a required rule result or authority act is absent, stale, denied, or indeterminate;
- contestability and preserved review history where required.

## Acceptance emphasis

- `AS-009` Rules and authority remain distinct;
- `AS-010` Positive authority provenance;
- `AS-011` Human modifies or rejects Recommendation;
- `AS-012` Human decision without Recommendation;
- `AS-013` Hold/no-action with zero Action Intents.

## Exit criteria

A consequential decision can be reconstructed from Evidence through Polaris judgment, deterministic rule results, power-specific authority acts, and Human Investment Decision without inferring one semantic layer from another.

# R5 — External action continuity and reconciliation

**Status:** Planned

## Objective

Close the gap between an attributable Human Investment Decision and authoritative external operational reality without giving Polaris execution authority.

## Product outcomes

The supported path must demonstrate:

- zero, one, or multiple Action Intents based on coherent intended consequence;
- Action Intent only after an attributable Human Investment Decision;
- Action Intent remaining distinct from Proposed Action, Order, fill, and broker instruction;
- observation of authoritative external activity and resulting Portfolio State;
- automatic reconciliation when association is sufficiently supported;
- explicit ambiguity when association is materially uncertain;
- partial, divergent, abandoned, or failed implementation remaining representable;
- unrelated external activity remaining externally initiated rather than being retroactively attributed to Polaris;
- authoritative operational reality overriding expected state;
- no market-facing execution authority in Polaris.

## Acceptance emphasis

- `AS-014` Action Intent and partial external implementation;
- `AS-015` Ambiguous reconciliation;
- `AS-016` Unrelated external activity;
- `AS-021` Operational reality overrides expectation.

## Exit criteria

For at least one supported consequential path, Polaris can preserve intended consequence and later reconcile authoritative external reality while keeping execution authority outside the product.

# R6 — Attentive closed-loop learning

**Status:** Planned

## Objective

Turn Durable Decision Memory from an archive into active product context so previous decisions, Review Conditions, assumptions, invalidation, Outcomes, Decision Evaluations, and Lessons influence what Polaris notices next.

## Product outcomes

The system must support all required initiation modes:

- user initiation;
- scheduled review;
- Polaris-detected Investment-Relevant material change.

It must also demonstrate:

- Investment Relevance distinct from Investment Materiality;
- quiet handling of irrelevant or immaterial change;
- memory-grounded Attention;
- prepared decision work rather than raw alerting where practical;
- correct same-unresolved-versus-new-linked-decision behavior;
- Review Conditions without reopening resolved history;
- Lessons affecting future Attention or Decision Context without silently becoming Policy, Mandate, or Formal Constraint;
- material-change triage that can invalidate current support before a full reasoning cycle completes.

## Acceptance emphasis

- `AS-001` New material Decision Need;
- `AS-002` Same unresolved decision resumes;
- `AS-003` Deferral and later resumption;
- `AS-004` Resolved decision followed by renewed judgment;
- `AS-020` Lesson affects future Attention;
- `AS-006` Stale Evidence blocks current support.

## Exit criteria

A prior decision can materially change what Polaris notices and how it frames later decision work, while resolved historical decisions remain immutable.

# R7 — Release hardening and 0.2.0 acceptance

**Status:** Planned

## Objective

Prove that the narrow supported system satisfies the approved 0.2.0 contract as one trustworthy product rather than as a collection of locally complete components.

## Required outcomes

- all 22 acceptance scenarios have executable or otherwise objective acceptance evidence;
- one coherent supported path satisfies the release acceptance gate end to end;
- integration failures, stale sources, missing Evidence, persistence failures, rule failures, authority failures, and reconciliation failures remain visible;
- retry and recovery preserve idempotent business truth;
- operational telemetry is sufficient to diagnose the supported path without becoming its business source of truth;
- secrets and sensitive Portfolio information are protected according to the chosen deployment model;
- at least one human-usable surface is complete for the supported path;
- configuration is expressed through investment-domain concepts rather than arbitrary workflow construction;
- measurable decision-time latency and reliability targets are defined and verified;
- no current production or test dependency reaches into `legacy/`;
- no requirement is accepted merely because a legacy component or runtime mechanism exists.

## Final release gate

0.2.0 is releasable only when the acceptance gate in [`../product/requirements-0.2.0.md`](../product/requirements-0.2.0.md) is satisfied in full.

The release may remain intentionally narrow in:

- asset universe;
- provider count;
- integration count;
- human surfaces;
- deployment modes;
- analytical breadth.

It may not remain semantically partial in the supported path.

# Donor-inspection strategy

Legacy salvage is not a milestone that runs once after architecture and then ends.

After R1 establishes current architectural owners, each later milestone should inspect only the donor areas relevant to the responsibility being implemented.

The sequence for any donor candidate is:

```text
current requirement
        ↓
current architectural owner
        ↓
current component boundary
        ↓
inspect relevant legacy donor
        ↓
KEEP LOGIC / TRANSPLANT / REWRITE / LEAVE
```

A donor is useful when its implementation independently fits the current owner and dependency direction. A donor is not useful merely because recreating it would take time.

Successful salvage includes discovering that an old component should not survive.

# Roadmap change control

This roadmap may change as architecture and implementation expose new information, but changes must preserve the approved product requirements unless the requirements themselves are explicitly reconsidered and re-approved.

Architecture may refine **how** milestones are delivered and identify technical dependencies. It must not silently convert architecture dependencies into new product requirements or reorder the roadmap around legacy subsystem boundaries.

A roadmap change should be explicit when it materially changes:

- milestone purpose;
- release scope;
- acceptance coverage;
- dependency ordering;
- authority boundary;
- external-system ownership;
- the supported end-to-end release path.

# Immediate next transition

If this roadmap is approved, the next substantive artifact is the **greenfield architecture** for R1.

That architecture should begin from the approved requirements and frozen domain model, establish ownership and dependency direction, and only then permit selective donor inspection.
