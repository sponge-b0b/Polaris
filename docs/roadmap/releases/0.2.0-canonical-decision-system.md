# Release identity

**Version:** 0.2.0  
**Name:** Canonical Decision System  
**Strategic stage:** Establish the decision system  
**Primary advancement type:** Lifecycle closure and capability integration  
**Supported breadth:** Deliberately narrow SPY portfolio-decision path

# Product thesis

> **A Polaris portfolio decision becomes durable shared product state independent of any one workflow execution.**

0.2.0 establishes the semantic center required by every later roadmap release.

The release is not primarily an improvement to the Morning Report workflow. It changes what Polaris treats as the product's authoritative unit.

The required transition is:

```text
Before 0.2.0

Workflow Execution
      ↓
workflow-owned evidence / reasoning / risk / outputs
      ↓
report-oriented product experience


0.2.0

Portfolio Decision
      ↓
shared decision lifecycle state
      ↓
workflow execution becomes optional orchestration beneath it
```

The release succeeds only if the Portfolio Decision lifecycle becomes independently meaningful and durable rather than merely being a new label placed around the existing workflow execution.

# Problem this release must solve

Polaris 0.1.0 already contains substantial evidence, reasoning, risk, governance, persistence, replay, evaluation, integration, and runtime machinery. The product-level weakness is that those strengths are organized primarily around Workflow Execution and its outputs.

As a result:

* useful decision behavior is disproportionately trapped inside the Morning Report path;
* workflow run identity acts as an accidental product identity;
* evidence, reasoning, risk, recommendation-like outputs, governance, and persistence do not yet join one canonical Portfolio Decision lifecycle;
* a report or completed run is easier to reconstruct than the portfolio decision the work was intended to support;
* governance approval and human investment judgment do not yet terminate in a first-class Human Portfolio Decision;
* interaction surfaces expose application/workflow fragments rather than a shared decision truth.

0.2.0 must correct that product center without discarding valuable existing mechanisms merely because their current ownership is wrong.

# Release boundary

0.2.0 establishes the canonical lifecycle through the **Human Portfolio Decision** boundary:

```text
Decision need
    ↓
Decision context + attributable evidence
    ↓
Investment reasoning + meaningful challenge
    ↓
Portfolio consequence + risk
    ↓
Recommendation
    ↓
Authority / admissibility state
    ↓
Human Portfolio Decision

Durable Decision Memory spans the lifecycle.
```

The release stops there deliberately.

0.2.0 does **not** require the later lifecycle segment:

```text
Human Portfolio Decision
    ↓
Action Intent
    ↓
External action
    ↓
Reconciliation
    ↓
Outcome
    ↓
Decision Outcome Evaluation
```

That closure belongs to 0.3.0.

# Supported operating envelope

0.2.0 must prove the product within a deliberately bounded context rather than dilute the release through breadth.

The supported release envelope is:

* one sophisticated individual operator or small-team operating model;
* one bounded portfolio context;
* SPY as the primary security and decision path;
* discretionary human investment authority;
* current market, macro, technical, news, sentiment, portfolio, and risk evidence sources only where needed by the supported SPY decision path;
* analytical / decision-time responsiveness rather than exchange-engine latency;
* existing CLI, MCP, and report mechanisms where they are useful projections or interaction paths;
* one or more runtime executions may serve a Portfolio Decision, but no runtime execution may define the identity of that decision.

Breadth beyond this envelope is not required to prove the release thesis.

# Required product contracts

## 1. Canonical Portfolio Decision identity

A supported decision must have one stable Portfolio Decision identity that represents the durable product concern being decided.

That identity must remain coherent across:

* multiple analyses;
* one or more runtime/workflow executions;
* process restarts;
* persistence and reconstruction;
* interaction surfaces;
* reports or other projections.

Workflow execution identity may remain useful operational metadata, but:

> **Workflow Run Identity ≠ Portfolio Decision Identity**

A Portfolio Decision must not cease to exist merely because one execution completed, failed, was replayed, or was replaced by another execution.

## 2. Decision initiation and continuity

A Portfolio Decision must be able to begin through at least one supported path without requiring the Morning Report workflow execution to be the decision's identity.

The release must preserve enough initiation context to answer at least:

* what decision is being considered;
* why decision work exists now;
* what portfolio/security context it concerns;
* what state of the decision is currently known.

0.2.0 does not require autonomous opportunity discovery or sophisticated attentive intelligence.

## 3. Decision-specific context and evidence

Material evidence used by the supported decision must be attributable to the Portfolio Decision rather than recoverable only through a workflow output or report.

The decision state must preserve the product-level relationship among:

* relevant context;
* evidence identity and provenance;
* material claims supported by that evidence;
* known evidence limitations relevant to the decision.

0.2.0 must integrate existing evidence semantics into the canonical decision lifecycle. It does not need to raise the full evidence capability to the 0.4.0 governed trust floor.

## 4. Reasoning and challenge as decision state

The Portfolio Decision must preserve material investment reasoning rather than only a final answer.

For the supported path, the decision state must be able to retain the meaningful product semantics already present in Polaris, including where applicable:

* thesis / interpretation;
* supporting evidence;
* contradictory evidence;
* meaningful alternatives or competing perspectives;
* assumptions;
* uncertainty;
* invalidation conditions;
* material risks or caveats.

The contract does not require a particular agent topology or debate mechanism.

## 5. Portfolio consequence and risk

The supported decision must be explicitly portfolio-aware.

Recommendation formation must be able to incorporate the actual bounded portfolio context and applicable analytical risk rather than producing only a generic market opinion about SPY.

The Portfolio Decision must preserve the material consequence/risk state needed to understand how portfolio circumstances shaped the recommendation.

## 6. Canonical Recommendation

0.2.0 must establish Recommendation as a first-class product semantic boundary.

A Recommendation is the Polaris decision-support conclusion presented for human consideration after the relevant evidence, reasoning, portfolio consequence, risk, and applicable authority constraints have been considered.

It must remain distinct from:

* a strategy hypothesis;
* strategy synthesis;
* an allocation calculation;
* trade packaging;
* an Action Intent;
* a governance approval;
* a Human Portfolio Decision;
* a report rendering.

The release may reuse existing outputs and contracts as ingredients, but none of those concepts may silently substitute for the canonical Recommendation.

## 7. Authority and admissibility remain distinct from human choice

Existing deterministic and governance authority semantics must remain visible in the canonical decision lifecycle.

The product must preserve the distinction:

> **Governance Approval ≠ Human Portfolio Decision**

and more completely:

> **What Polaris recommended ≠ what governance permitted ≠ what the human decided**

0.2.0 does not require a second governance engine. It requires existing authority machinery to participate correctly in the Portfolio Decision lifecycle.

## 8. First-class Human Portfolio Decision

The lifecycle must terminate, for this release, in a first-class Human Portfolio Decision.

For the supported path, the human must be able to record a decision such as:

* accept;
* modify;
* reject;
* defer.

The Human Portfolio Decision must preserve its relationship to the Recommendation and the applicable authority/admissibility state while remaining a separate fact.

Where the human supplies rationale or modifications, Polaris must be able to preserve them as part of the decision lifecycle.

0.2.0 does not require translating the Human Portfolio Decision into broker execution or authoritative external action.

## 9. Durable Decision Memory through the release boundary

The material lifecycle through Human Portfolio Decision must be durable and reconstructable.

A later process must be able to recover the decision's material state without treating any of the following as the source of truth:

* a rendered Morning Report;
* a conversation transcript;
* an ephemeral workflow context;
* a single completed-run record.

Existing persistence mechanisms should provide implementation ingredients, but the product-level requirement is:

> **Persistence ≠ Durable Decision Memory**

Durability is successful only when the stored state reconstructs the Portfolio Decision as a coherent lifecycle.

## 10. Direct product interaction independent of the complete Morning Report

At least one supported interaction path must be able to inspect or advance canonical Portfolio Decision state without executing the complete Morning Report workflow.

The direct path need not be a new UI.

CLI or MCP may satisfy this contract if they expose canonical application behavior rather than reimplement decision semantics at the transport boundary.

The product claim fails if the only practical way to use the canonical decision capabilities remains “run the Morning Report and inspect its output.”

## 11. Morning Report becomes a consumer, not a competing product truth

The Morning Report may remain an important product experience and orchestration path.

For 0.2.0, however, it must consume or project the same canonical Portfolio Decision semantics used by direct product interaction.

It must not independently create a parallel version of:

* decision identity;
* Recommendation;
* authority state;
* Human Portfolio Decision;
* durable decision history.

The governing rule is:

> **Preserve the Morning Report as a use case where valuable; remove its accidental ownership of the product model.**

# Capability envelope

The release advances the capabilities required to establish one integrated canonical decision lifecycle through Human Portfolio Decision.

| Capability | 0.1.0 baseline | 0.2.0 contract |
| --- | ---: | ---: |
| Attention & Decision Initiation | M1 — Bounded | **M2 — Integrated** |
| Decision Context & Evidence | M1 — Bounded | **M2 — Integrated** |
| Investment Reasoning & Challenge | M1 — Bounded | **M2 — Integrated** |
| Portfolio Consequence & Risk | M1 — Bounded | **M2 — Integrated** |
| Recommendation Formation | M1 — Bounded | **M2 — Integrated** |
| Authority & Human Decision | M1 — Bounded | **M2 — Integrated** |
| Durable Decision Memory | M0 — Ad hoc | **M2 — Integrated** |
| Interaction & Projection | M1 — Bounded | **M2 for the supported decision projection** |
| Runtime Reliability & Observability | M1 — Bounded | **M2 for decision-linked runtime work** |

The following capabilities are intentionally not required to advance in 0.2.0:

| Capability | 0.2.0 requirement |
| --- | --- |
| Action Continuity & Reconciliation | May remain **M0 — Ad hoc** |
| Outcome Evaluation & Learning | May remain **M0 — Ad hoc** |
| Integration & Connectivity | Existing bounded capability may remain **M1**, except where integration changes are required to satisfy the canonical decision path |
| Configuration & Extensibility | Existing bounded capability may remain **M1** |
| Security & Operations | May remain **M0 — Ad hoc** within the explicitly bounded pre-1.0 operating assumptions |

M2 has its strict Capability Model meaning: the capability participates in the canonical Polaris decision lifecycle and exchanges correct shared product semantics with adjacent capabilities.

0.2.0 therefore does not earn M2 merely because individual subsystems are locally sophisticated.

# Required semantic invariants

The release must preserve these distinctions across implementation and interaction surfaces:

> **Workflow Execution ≠ Portfolio Decision**

> **Workflow Run Identity ≠ Portfolio Decision Identity**

> **Strategy Synthesis ≠ Recommendation**

> **Portfolio Allocation Intent ≠ Human Portfolio Decision**

> **Trade Packaging ≠ Human Portfolio Decision**

> **Governance Approval ≠ Human Portfolio Decision**

> **What Polaris recommended ≠ what governance permitted ≠ what the human decided**

> **Persistence ≠ Durable Decision Memory**

> **Report Output ≠ Canonical Decision State**

Additional release invariants are:

* Portfolio Decision is the product center for the supported path;
* AI remains a reasoning participant, not investment authority;
* deterministic software retains ownership of deterministic guarantees and policy where appropriate;
* consequential investment judgment remains human;
* existing strong mechanisms should be reused and re-parented rather than duplicated without necessity;
* pre-1.0 compatibility must not preserve an incorrect workflow-centric product model;
* implementation topology is subordinate to the product semantics defined here.

# Preservation and change doctrine

0.2.0 is a semantic and dependency inversion, not an indiscriminate rewrite.

The release should preserve useful existing mechanisms where they satisfy the corrected product responsibility, including the current families of:

* evidence provenance, claim binding, readiness, reconstruction, and persistence;
* structured hypotheses, challenge, synthesis, assumptions, and invalidation semantics;
* portfolio state and analytical risk;
* deterministic policy and governance;
* PostgreSQL durability;
* runtime execution, checkpoints, replay, health, and telemetry;
* provider boundaries and dependency injection;
* CLI/MCP/report projection mechanisms.

The release contract does not require these mechanisms to retain their current ownership or call graph.

The governing change rule is:

```text
preserve useful semantics
        ↓
attach them to the correct product responsibility
        ↓
remove accidental Workflow Execution ownership
```

# Product acceptance

0.2.0 is product-complete only when one supported SPY decision demonstrates the release thesis end to end.

A canonical acceptance demonstration must prove all of the following.

## Identity and initiation

1. One stable Portfolio Decision identity exists.
2. The decision can be initiated without using a Morning Report workflow run as its product identity.
3. Additional analysis or runtime executions can contribute to the same decision without creating a new product truth accidentally.

## Integrated decision state

4. Decision-specific evidence/context is inspectable as part of the Portfolio Decision.
5. Material reasoning, challenge, assumptions, uncertainty, alternatives, and invalidation semantics required by the supported path are connected to the same decision.
6. Actual portfolio consequence and analytical risk materially shape the decision state.
7. A canonical Recommendation exists and is distinguishable from upstream reasoning/synthesis and downstream human choice.
8. Applicable authority/admissibility state is inspectable and distinct from the Recommendation.
9. A Human Portfolio Decision can be recorded as a separate durable fact.

## Durability

10. After process restart, a later process can reconstruct the material lifecycle through Human Portfolio Decision from durable state.
11. Reconstruction does not depend on parsing a report, recovering an ephemeral workflow context, or treating a completed workflow run as the decision itself.

## Independent product access

12. At least one supported product interaction path can directly inspect or advance the Portfolio Decision without running the complete Morning Report.
13. The Morning Report, if retained, consumes or projects the same canonical decision semantics rather than maintaining parallel decision truth.

## Semantic integrity

14. The product can answer, as distinct facts:

```text
What decision is being considered?
What evidence and context support it?
What reasoning and challenge were preserved?
How did portfolio state and risk shape it?
What did Polaris recommend?
What did governance / deterministic authority permit or constrain?
What did the human decide?
```

15. None of those answers requires substituting a workflow output merely because the corresponding product semantic is absent.

If these conditions are not demonstrably true inside the supported envelope, 0.2.0 is not complete even if all planned engineering tickets are closed.

# Explicit non-goals

0.2.0 does not require:

* broker order or fill reconciliation;
* Action Intent as a complete product capability;
* authoritative observation of what was executed externally;
* realized portfolio-outcome evaluation;
* decision-quality learning from realized outcomes;
* active or adaptive learning;
* broad autonomous attention or opportunity discovery;
* additional brokers;
* additional asset classes;
* broad portfolio-model support;
* generalized screening;
* a quantitative-research environment;
* autonomous market-facing execution;
* high-frequency / low-latency trading infrastructure;
* a new web application or dashboard;
* enterprise IAM or broad institutional compliance operations;
* a new generic workflow engine;
* a new generic agent framework;
* a second persistence framework;
* a second evidence framework;
* a second governance engine;
* infrastructure replacement that does not materially enable the release contract.

# Release failure conditions

The release should be considered architecturally or product-semantically incorrect if any of the following become true:

* Portfolio Decision is only a wrapper around one workflow execution;
* Morning Report remains the only practical path to the decision capability;
* workflow run ID remains the effective durable decision identity;
* Recommendation is merely a rename of strategy synthesis, allocation intent, or trade packaging without a distinct product contract;
* governance approval is treated as the Human Portfolio Decision;
* Human Portfolio Decision is inferred from a recommendation or workflow completion rather than recorded as its own fact;
* durable decision reconstruction depends on reports or ephemeral execution state;
* direct surfaces independently reconstruct decision semantics instead of projecting canonical state;
* the release introduces duplicate evidence, governance, persistence, or runtime systems without a demonstrated inability of the existing mechanism to satisfy the corrected responsibility;
* compatibility with the 0.1.0 topology is prioritized over the correct Portfolio Decision model.

# Requirements handoff

Once this release contract is approved, the 0.2.0 requirements specification should derive concrete, testable requirements from this contract without yet choosing implementation topology.

The requirements phase should answer at minimum:

1. What information must define and identify a Portfolio Decision?
2. What lifecycle states and transitions must be representable through Human Portfolio Decision?
3. What decision context and evidence relationships must be durable?
4. What reasoning/challenge semantics must be preserved and associated with the decision?
5. What portfolio consequence and risk semantics must participate in Recommendation formation?
6. What information must the canonical Recommendation contain or reference?
7. What authority/admissibility state must be represented separately from human judgment?
8. What must a Human Portfolio Decision record?
9. What durability and reconstruction guarantees must hold?
10. What direct interaction behavior proves independence from the complete Morning Report workflow?
11. What behavior must the Morning Report preserve after it becomes a consumer/orchestrator of canonical decision semantics?
12. What legacy behavior may be broken or deprecated because it conflicts with the corrected product model?

The requirements specification should remain implementation-neutral enough that the subsequent architecture phase can evaluate how the strongest existing Polaris mechanisms should be re-parented to satisfy those requirements.
